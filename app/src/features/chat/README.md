# 채팅 런타임 작업 중

채팅 화면과 라우트에 연결했다. 실제 서버와 기기 검증은 남았다.

- `createChatApi`는 요청 함수를 주입할 수 있다. 기본 요청은 공통 `apiRequest`를 사용한다.
- `parseMatch`는 역할에 따른 지도 이름의 타입을 유지한다. `parseMessage`는 senderId를 UUID 문자열로 검증한다.
- `ChatRoomController.configure`에는 계정, 토큰, 역할, 매칭 ID, 포커스 및 foreground 상태를 넘긴다. 활성 상태에서 8초 간격으로 조회하고 이탈 시 조회와 타이머를 정리한다. `dispose` 이후 재사용하지 않는다.
- 신규 메시지는 서버가 준 ID로만 전진한다. 한 차례 최대 10페이지를 읽고 마지막 페이지가 가득 찼으면 `backlog`를 유지해 100ms 뒤 이어 읽는다. 이는 회당 요청 예산이며 메시지 개수 제한이 아니다.
- 신규 메시지를 따라잡은 뒤에는 매 주기 과거 50개씩 처음부터 순환 조회해 오래된 번역과 읽음 변경도 갱신한다. 메시지 수가 N개로 유지되면 빈 페이지 확인을 포함한 한 바퀴에 약 `(floor(N / 50) + 1) * 8초`가 걸리고 매 주기 상세 1회와 신규 조회 1회, 과거 조회 1회가 발생한다. 서버 지연과 추가 backlog에 따라 더 오래 걸릴 수 있다. 조회마다 상대 메시지 읽음 처리가 발생한다.
- 전송 결과가 불확실하면 초안을 유지하고 자동 재전송하지 않는다. 사용자가 공통 확인 시트에서 재시도를 명시한 경우에만 `acknowledgeUncertainSend`를 호출한다.
- 실제 서버의 메시지 GET은 읽음 상태를 변경하므로 자동 검사에서 호출하지 않는다.
- 전송 응답은 본인 여부와 UUID, 원문을 대조한다. 저장 가능성이 남는 오류는 불확실 상태로 유지한다. 결정적 거절도 상세를 다시 조회한다. 상세를 확인하지 못한 동안은 전송을 막으며, 종료 상태 또는 접근 거절을 확인하면 기존 메시지를 숨긴다.
- 기존 상세가 유효한 상태에서 폴링 조회 중 전송하면 조회를 취소하고 늦은 조회 결과를 버린 다음 전송한다. 서버의 전송 거절은 처리 후 상세를 다시 조회한다.
- `ChatListController`는 계정, 역할, 지도 필터별로 결과를 분리하고 빠른 갱신의 늦은 결과를 버린다. 목록 조회 자체는 반복 타이머를 두지 않는다. 화면 포커스와 foreground 변경을 전달하고 `dispose` 이후 재사용하지 않는다.
- 컨테이너는 첫 렌더에서도 snapshot의 계정, 매칭 또는 역할과 지도 필터를 현재 세션과 대조하고 일치하지 않는 결과를 표시하지 않는다. 메시지 발신자는 현재 계정 또는 매칭 상대여야 하며 `mine`과 발신자 일치 여부도 검사한다.
- 열기 결과가 불확실한 시트의 확인 동작은 `open`이 아니라 `refresh`에 연결한다. 상세 확인 이후에도 열 수 있는 상태이고 사용자가 다시 선택한 경우에만 `open`을 호출한다.
- 불확실 전송은 공통 확인 시트에서 이력 확인과 중복 가능성을 안내하고 명시적으로 확인한 뒤에만 재전송한다.
- 메이트는 명시적 토큰으로 본인 지도 목록을 불러오고 지도별 대화를 필터링한다. 지도 목록은 계정과 토큰별로 유지하며 필터 변경만으로 다시 조회하지 않는다.
- 채팅 메뉴에 상대 프로필 신고와 차단을 연결하고 상대 메시지에서 해당 메시지 신고를 선택할 수 있다. 신고와 차단의 실제 서버 및 실기기 검증은 남았다.
- 완료된 매칭은 기존 메시지를 조회하되 새 대화를 열거나 메시지를 보내지 않는다. 서버 DTO의 `canOpen` 검증과 앱 표시 정책은 별개다.
