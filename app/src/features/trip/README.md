# 여행 일정 데이터 모듈

일정 전용 화면과 route를 작성하고 공용 진입 경로에 연결했다. `model.ts`는 `isDate`, `seoulToday`, `parseTrip`, `validateDates`, `sameTrip`을 제공한다. `api.ts`는 `getCurrentTrip`, `createTrip`, `patchTrip`과 주입 가능한 `TripRequest`를 제공한다. `saveFlow.ts`의 `createTripSaveFlow`에 토큰, 필수 계정 소유 확인 함수와 선택적 AbortSignal 및 mock 요청을 전달한다. `load`로 원본을 불러오고 `save(original, desired, today)`에 원본과 입력을 별도로 넘긴다. 화면별로 한 흐름 인스턴스를 유지해야 중복 제출이 차단된다.

`today`는 `seoulToday`로 계산하고 테스트는 고정 시각을 주입한다. 신규 시작일과 종료일은 오늘 이후여야 한다. 기존 진행 일정의 과거 시작일은 유지할 수 있지만 다른 과거 날짜로 변경할 수 없다. 서버는 시작일 자체의 과거 여부는 검사하지 않고 종료일과 순서만 검사한다.

404 중 TRIP_NOT_FOUND만 없음으로 변환한다. 저장 전 최신 원본이 다르면 conflict를 반환하고 다시 조회와 사용자 확인이 필요하다. POST의 TRIP_EXISTS는 재조회하며 날짜가 일치할 때만 복구한다. 네트워크 오류나 시간 초과, 성공 응답 뒤에도 재조회하여 요청 날짜와 알려진 ID를 확인한다. 신규 POST가 응답 전에 실패하면 생성 ID를 알 수 없어 날짜 일치만 확인할 수 있다. 이는 동일 날짜의 동시 생성과 구분할 수 없는 서버 계약의 한계이므로 성공으로 처리하지 않고 unconfirmed를 반환한다. 재조회 실패나 불일치는 unconfirmed이며 사용자에게 다시 확인하도록 안내해야 한다. 취소와 계정 전환은 결과 반영과 후속 쓰기를 막지만 이미 전송된 요청의 서버 처리까지 취소했다고 보장하지 않는다. 화면 재진입 시 반드시 다시 조회한다. 실제 서버와 기기 검증은 남았다.

계정별 화면 수명 동안 인스턴스 하나를 유지하고 계정이 바뀌거나 signal이 취소된 뒤에는 새 인스턴스를 만든다. 토큰은 필수이며 빈 토큰으로 현재 세션에 대체 접근하지 않는다. 생성 시 전달 설정을 복사한다.

서버에 버전 또는 조건부 갱신 계약이 없으므로 저장 전 조회와 PATCH 사이에 발생하는 동시 변경은 원자적으로 차단할 수 없다. 실제 기기에서 Intl을 이용한 서울 날짜 계산은 아직 검증하지 않았다.

## 달력 화면

`TripScreen`은 `userId`, 토큰, origin, 계정 소유 확인, 회원 상태 재조회와 이동 콜백을 받는다. `request`와 `now`는 검사에 주입할 수 있다. 새 `trip.tsx`는 여행자와 본인 확인, 프로필, 취향, 조건의 준비 상태를 검사한다. 저장 확인과 회원 상태의 trip 완료 확인 뒤에만 온보딩 홈 또는 계정 화면으로 이동한다. 이전 조건 화면은 이 작업본에서 아직 연결되지 않아 뒤로가기는 account로 이동한다. users의 단계 경로와 account의 일정 등록 및 재편집 진입은 연결했다. 조건 화면과 이전 단계 복귀는 후속 작업이다.

현재 일정의 과거 시작일을 유지하며 귀국일 선택 카드에서 종료일을 수정할 수 있다. 입력은 계정별 메모리 초안으로 단계 왕복 중 보존되며 계정 변경 시 격리한다. 실서버 저장과 실제 폰 레이아웃, Android 뒤로가기 및 Intl 시간대 계산은 확인하지 않았다.

초안 소유권은 `draft.ts`의 `syncTripDraftAccount`로 관리한다. SessionProvider의 계정 동기화 effect에서 이 함수를 호출하여 화면 밖 로그아웃과 계정 전환에도 초안이 폐기된다. 자동 재조회에서 서버 원본이 바뀌면 입력을 보존하고 저장을 막으며 사용자가 재읽기를 눌렀을 때만 교체한다. 서울 자정과 앱 복귀 및 저장 직전에 오늘을 재계산한다.
